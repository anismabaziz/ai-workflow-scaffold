# AGENTS.md

## Ignore rules

`.plan/` and this file (`AGENTS.md`) are planning artifacts, not codebase
context, and neither is committed (both stay local to the machine). Agents do
not treat them as product code. What agents may read and write inside `.plan/`
is defined by the workflows below (tickets, specs, PR bodies, review replies,
blog drafts); everything else in `.plan/` stays untouched. The committed
`examples/` folder shows the exact formats these artifacts use.

## Workflow for refactors and features

Whenever working on a refactor or adding a feature, keep all planning
artifacts under `.plan/`:

- Tickets generated by `/to-tickets` go under `.plan/tickets/`, in a folder
  named `<day>-<summary>` where `<day>` is the date (`YYYY-MM-DD`) and
  `<summary>` is a short hyphen-separated summary of the ticket batch. One
  `.md` file per ticket inside that folder (never a single combined file).
- Specs generated by `/to-spec` go under `.plan/spec/`.

## Pull requests

For each pull request, store the pull request body under
`.plan/pull-requests/`. A pull request can bundle several ticket groups. The
file name matches the branch the PR is on, with slashes replaced by hyphens,
so `fix/foo-bar` has its PR body in `pull-requests/fix-foo-bar.md`.

Follow the pull request format in `.github/pull_request_template.md`. When
generating it, load and apply the `unslop` skill.

## Review replies

Reviewer comments are kept under `.plan/review-replies/`, with one folder per
pull request named after the pull request file (the branch, slashes replaced
by hyphens). Each review iteration is a numbered file inside that folder,
starting at `1.md` and incrementing for each new review round.

Inside each iteration file, paste the reviewer's general comment, if any, then
every inline review comment. After each comment, leave a reserved section for
its reply. When a ticket that resolves the comment is implemented, write the
reply in that reserved section. Apply the `unslop` skill to the replies and to
the translations.

## Blog drafts

Project blog writing lives in `.plan/blog/`, one `.md` file per post named
`<day>-<slug>.md`. Drafts are not product code; an agent may help write and
edit them on request, using the template in `examples/blog/README.md`. Apply
the `unslop` skill to anything that will be published.

## Writing

Whenever writing any human-facing text, including chat replies to the user,
load and apply the `unslop` skill to remove AI writing patterns and keep the
voice human.
