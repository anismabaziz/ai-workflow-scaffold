# AGENTS.md

## Ignore rules

`.plan/`, `CONTEXT.md` and this file (`AGENTS.md`) are planning artifacts, not
codebase context, and not committed (all stay local to the machine).
Agents do not treat them as product code. `CONTEXT.md` is the domain glossary,
maintained by the `domain-modeling` skill. What agents may read and write
inside `.plan/` is defined by the workflows below (tickets, specs, PR bodies,
review replies, blog drafts) plus `.plan/other/` for everything else; anything not covered
stays untouched. The committed `examples/` folder shows the exact formats these
artifacts use.

## Planning artifact references — forbidden in committed content

Never mention planning artifacts anywhere in the codebase or in any committed
content: code, tests, comments, docs, commit messages, or GitHub PR
descriptions. That includes ticket numbers or names (e.g.
`02-...`, `TKT-...`), ticket/spec file paths, `.plan/` paths, and
`CONTEXT.md`. If you need to explain a change, describe the feature itself —
what it does and why — without linking it to a planning artifact.

The artifacts stay local. The codebase stays clean.

## Process vocabulary — forbidden in committed content

The ban above covers internal process vocabulary too. Words like seam and
tracer bullet come from planning and skill workflows, so they never appear in
committed content either: not in code, tests, comments, docs, commit messages,
or PR descriptions. When you need the concept, say it in plain domain language
instead. Storage access goes through a single place in the repository. If you are unsure whether a word is process jargon, leave it out.

## Workflow for refactors and features

Whenever working on a refactor or adding a feature, keep all planning
artifacts under `.plan/`:

- Tickets generated by `/to-tickets` go under `.plan/tickets/<branch>/<NN>-<summary>/` where `<branch>` is the current branch with `/` replaced by `-`, `<NN>` is a zero-padded sequence per branch (`01`, `02`, …), and `<summary>` is a short hyphen-separated summary of the ticket batch. One `.md` file per ticket inside that batch folder (never a single combined file).
- Specs generated by `/to-spec` go under `.plan/spec/<branch>/<NN>-<summary>.md` where `<branch>` is the current branch with `/` replaced by `-`, `<NN>` is a zero-padded sequence per branch (`01`, `02`, …), and `<summary>` is a short hyphen-separated summary. Drop the `YYYY-MM-DD` prefix. Specs stay local in `.plan/` — do not create or publish GitHub issues for them.
- When a ticket is done, mark it in its file: set `**Status:**` to `done` (was `ready-for-agent`) and check every box (`- [ ]` → `- [x]`). The ticket file is the progress tracker; if it still says `ready-for-agent`, the next agent will assume it is untouched.

## Implementation

When implementing with the `implement` skill, follow this order: implement
the change, run `code-review` on it, fix the findings (or record why a
finding does not apply), then commit. Do not commit before the review and
its fixes are done.

## Pull requests

For each pull request, store the pull request body under
`.plan/pull-requests/<branch-with-hyphens>.md`. A pull request can bundle several ticket groups. The
file name matches the branch the PR is on, with slashes replaced by hyphens,
so `fix/foo-bar` has its PR body in `pull-requests/fix-foo-bar.md` (`.plan/pull-requests/fix-foo-bar.md`).

Follow the pull request format in `examples/pull-requests/example-pr.md`. Write
the body in English. When generating it, load and apply the
`unslop` skill.

## Review replies

Reviewer comments are kept under `.plan/review-replies/`, with one folder per
pull request named after the pull request file (the branch, slashes replaced
by hyphens). Each review iteration is a numbered file inside that folder,
starting at `1.md` and incrementing for each new review round.

Inside each iteration file, paste the reviewer's general comment, if any, then
every inline review comment. After each comment, leave a reserved section for
its reply. When a ticket that resolves the comment is implemented, write the
reply in that reserved section. Write all replies in English; translate any
non-English comments to English. Apply the `unslop` skill to the replies and to the translations.

Tying tickets to replies — required: when a ticket batch exists to fix review feedback (e.g. `16-pr99-review-round-1-fixes`), filling the replies is part of implementing the tickets, not a follow-up. As each ticket is completed, also update its matching reply in `.plan/review-replies/<branch>/N.md`: replace the `<!-- TODO -->` placeholder with the actual fix — ticket ID, spec file, commit hash(es), `file:line` references, and the test or lint evidence that proves it. A review-fix ticket is not done while its reply still contains a TODO. The `implement` workflow must check this before considering the batch complete.

## Code review (PRs from other members)

Reviewing someone else's PR is a different flow from "Review replies", which
tracks the comments you receive on your own PRs. This one is for PRs coming in
from the rest of the team. Two artifact folders:

- `.plan/incoming-prs/` — the reviewed PR's body, one file per PR named after
  the branch (slashes replaced by hyphens). Collected during the gather phase,
  stored in English (translate any non-English content, with `unslop` applied
  to the translation). This is what the code is compared against.
- `.plan/outgoing-reviews/` — the review drafts, one folder per PR named after
  the branch, one numbered file per review pass (`1.md`, `2.md`, …). Written
  only when the review finds issues.

Gather phase — shared sources only, never `.plan/`:

1. Diff the branch against the merge-base with `main` (`git diff
   main...<branch>`) and list its commits.
2. Check CI status: flag red checks first, and don't re-review anything tooling
   already enforces (ruff, pytest, lint, build, secret scan).
3. Fetch the GitHub PR body and store it in `.plan/incoming-prs/` in English
   (translate any non-English content).
4. When the PR references an issue, fetch it (`gh issue view N`): it is the
   spec the PR claims to solve.
5. When the PR references a spec, fetch it as well (`gh pr view N` for the PR
   body source). Note the committed docs the PR cites as its requirement source.

Analysis — via the `code-review` skill:

- A PR that closes an issue is reviewed along two axes: Standards (repo docs +
  smell baseline) and Spec, against the open issue it solves and the stored PR
  body.
- A feature PR with no issue gets no issue comparison: Standards plus Spec
  against the PR body's declared intent.

Draft:

- When the review finds issues, write the draft to the pass file: general
  comment drafts, and inline review comments each pointing at exactly where the
  edit belongs. Post the review on GitHub yourself; the file is the working
  draft, not a substitute for the review.

Iterate:

- When the author pushes again, start the next pass (increment the number) and
  check whether the requested changes were addressed.

Rules:

- The reviewer is distinct from the lead (per the PR template).
- Never merge the two axes into a single verdict: a change can pass one and
  fail the other.

## Blog drafts

Keep project-related writing under `.plan/blog/`, one `.md` file per post. This folder is local-only like the rest of `.plan/`. Draft in any order; when a post is published, move the file to your blog source. Name files `<NN>-<slug>.md` where `<NN>` is a zero-padded number (`01`, `02`, …) — for example `01-my-post.md`. The committed `examples/blog/01-example-draft.md` shows the exact format. Starting template:

```markdown
# Title

Status: draft

## The hook

Why does this matter? What will the reader get from it?

## The story

- What problem were you solving?
- What did you try, what surprised you?
- What ended up working?

## The takeaway

What would you do differently? What should the reader steal?
```

## Other

Any file that doesn't belong to the workflows above goes under `.plan/other/`.
Freeform structure, never committed, not treated as product code. Use it for
notes, scratch docs, investigations, or temporary exports that don't fit a
workflow.

## Commit messages

Commit messages follow the conventional format `<type>: <subject>`, where
`<type>` is the purpose of the change and `<subject>` is a short imperative
summary. Example: `feat: Add cart to ecom store`.

Common types:

- `feat`: new feature
- `fix`: bug fix
- `refactor`: behavior-preserving change
- `docs`: documentation only
- `chore`: tooling, dependencies, maintenance
- `test`: tests only
- `style`: formatting, no behavior change
- `perf`: performance improvement
- `build`: build system or dependencies
- `ci`: CI configuration
- `revert`: revert a previous commit

## Writing

Whenever writing any human-facing text, including chat replies to the user,
load and apply the `unslop` skill to remove AI writing patterns and keep the
voice human.
